# CatCrewAI architecture

CatCrewAI is three cooperating parts: a **Python backend** that owns every agent, task and file; a **local HTTP + WebSocket API** in front of it; and a **Tauri + React desktop UI** that is a pure client of that API. This document describes how it works as it is built today. Where the implementation differs from an intended design the difference is called out, and the fix is tracked in [`todo/TECHNICAL_DEBT_AND_OPTIMIZATIONS.md`](../todo/TECHNICAL_DEBT_AND_OPTIMIZATIONS.md). The wire contract is [`API.md`](API.md).

## 1. Layout and process model

```
  Tauri shell (Rust, frontend/src-tauri)             starts / stops the backend, owns the native window
      |  loads
      v
  React UI (frontend/src)  --REST /api/*-->  FastAPI (backend/api)  ---> ChatService (core/chat_service.py)
        ^                 <--WS /ws/events--  EventHub (api/events.py)         |  one turn at a time, on a worker thread
        |                                          ^                          v
        |                                          |   platform/bus  <---  SOP / runner / delegation engine
        |                                          |   (thread-safe)        (asyncio thread, RunSupervisor)
        +---- state/reducer.ts applies each event  +----- publishers:              |  asyncio.to_thread(run_bot)
                                                        activity board,             v
                                                        task ledger, chat     providers -> tools -> SQLite / files / shell / web
```

| Path | Contents |
| --- | --- |
| `backend/api/` | FastAPI app, routes (`projects`, `agents`, `tasks`, `chat`, `skills`, `tools`, `models`, `meta`), the WebSocket hub, the local-only guard, wire views |
| `backend/core/` | `ChatService` (turns, queueing, steering, approvals), wire message shapes, the async run supervisor and engine, the agent loop adapters |
| `backend/platform/` | Bots, projects, SOP pipeline, Cat Crew (orchestrator: identity, intent router, hand-off), delegation, roster, runner, activity board, event bus, auto-skill builder |
| `backend/db/` | `ledger.py` (operations ledger, SQLite) and `state/` (run store), `legacy.py` (old module path mapping) |
| `backend/harness/`, `providers/`, `tools.py`, `services/` | Approvals and ask-user, model providers, built-in tools, sessions, memory, workspace, git, search, ... |
| `backend/middleware/` | `jev_gatekeeper.py`: the Jev ("System One") pre-execution gatekeeper (see section 9) |
| `backend/skills/`, `backend/tool_functions/` | Anthropic-style Markdown playbooks and Letta-style Python tools |
| `backend/config/`, `integrations/` | `mcp_servers.json` (the MCP servers CatCrewAI connects to) and the helpers that set up the other side: `integrations/blender/install_addon.py`, `integrations/unity/CatCrewUnityMCP.cs` + `install_unity_helper.py` |
| `frontend/src/` | React app: `pages/`, `components/`, `state/` (reducer, store, socket), `lib/` (typed API client, time, window) |
| `frontend/src-tauri/` | Tauri 2 shell: window config, capability file, `lib.rs` (backend lifecycle) |
| `docs/`, `todo/`, `scripts/`, `tests/` | Documentation, the debt backlog, seeders and dev tools (`scripts/dev_fake_llm.py`), the Python tests |

Threads on the backend: the uvicorn event loop (async routes and the WebSocket hub); FastAPI's worker pool for synchronous routes; one turn thread (`ChatService` runs a single turn at a time, and queues the next message); the delegation engine's asyncio thread; and `asyncio.to_thread` workers for each specialist run. Nothing that blocks (an LLM call, a shell command, a SQLite write) runs on the event loop.

## 2. The API and the live event stream

REST answers "what is the state now"; the WebSocket answers "what just changed". Every writer of live state publishes to the in-process bus (`platform/bus.py`); the API subscribes once and fans events out.

- **Bus.** Pure Python and thread-safe. `publish` never blocks; subscribers run on the emitting thread and must be cheap. Events carry ids, not rows. A failing subscriber cannot break a DB write or an agent turn.
- **Hub** (`api/events.py`, `api/ws.py`). Each WebSocket client gets a bounded asyncio queue (2000 frames). The bus callback only does `loop.call_soon_threadsafe(queue.put_nowait, ...)`; the row is read and turned into its wire shape (`enrich`) on the loop side, off the emitting thread. A client that cannot keep up is closed with 1013 and reconnects; there is no replay, so the first frame of every connection is `hello {server_seq}` and the client refetches over REST.
- **Envelope.** `{v, seq, ts, type, project_id, data}`. Types: `bot.staffed`, `bot.released`, `bot.activity`, `phase.started`, `task.changed`, `file.changed`, `chat.message`, `chat.activity`, `turn.started/finished/failed`, `approval.*`, `ask.*`, `skill.proposed`, `project.changed`, `context.usage`.
- **The orchestrator call is instant.** When Cat Crew (the orchestrator) picks a specialist, staffing publishes `bot.staffed` in the same call; the UI adds the cat to the Fleet sidebar with a pop-in animation before the cat has produced a single token. Verified order for one specialist: `turn.started`, `bot.activity(chief thinking)`, `bot.staffed`, `task.changed`, `phase.started`, `bot.activity(thinking -> coding)`, `chat.activity` steps, `file.changed`, `bot.activity(idle)`, `task.changed(done)`, `chat.message`, `project.changed`, `turn.finished`.
- **Local-only.** The server binds to loopback and a pure-ASGI guard (`api/security.py`) rejects any HTTP or WebSocket request whose `Host` is not a loopback name or whose `Origin` is not on the allow-list (the Tauri webview and the Vite dev server). This stops a web page in the user's browser from driving an API that can run shell commands. No endpoint returns a secret.
- **Auto-skill builder.** After a successful task `platform/auto_skill.py` may propose a playbook; it appears at `GET /api/skills/proposals` and as a `skill.proposed` event and needs a person's approval.

## 3. Context isolation pattern

A specialist must never see the global conversation. What it receives is assembled in `platform/runner.run_bot`:

1. The bot's own system prompt from the catalog, plus the non-negotiable execution rules and the role-specific addendum (`developer`, `devops`, `qa`, ...).
2. `_project_context()`: project name and description, the shared computer folder, the ten most recent file changes (path, who, when; never diff bodies) and the workspace `AGENTS.md` / `SYSTEM.md` from the attached folder. It deliberately does not include project chat events or the raw `project.state` blob.
3. The assigned task text, built per phase in `platform/sop.py` (work orders, `_direct_task`), which carries the original brief and the task id the specialist must report against.
4. `extra_context`: the hand-off from earlier phases (see the note below) and the kickoff brief.
5. A skills index filtered to what that bot is assigned (name and description only).
6. Its own tool schemas: role-filtered built-ins (`builtin_names_for_role`) plus the tools bound to it in `agent_tools`, registered for this turn only.

The run's provider and abort callback are captured on the calling thread before crossing onto the engine thread. The workspace folder set is switched to the project's computer for the run and restored afterwards.

Known gap: the SOP accumulates the full text of every earlier phase into one string (`prior`) and passes all of it to each later specialist, so context grows with each phase instead of being limited to the artifact and diffs the next role needs. See item C-01 in the backlog.

### The tool loop: hooks, pruning, repeats, queue

Every agent turn (a 1:1 chat, Cat Crew's chat, each SOP specialist, a subagent) runs the same loop, `BaseProvider.run_agent` (`providers/base.py`). The parts that shape it, modelled on OpenClaw's agent runtime:

- **Lifecycle hooks** (`harness/hooks.py`). Each tool call goes through a `before_tool_call` chain (may rewrite `ctx.arguments`; returning a string blocks the call and becomes its result; a hook that raises blocks it, fail closed) and an `after_tool_call` chain (returns the result to record; a hook that raises is skipped). Built-ins in order: approval gate (10), Jev (20); large-result offload (10), untrusted-content wrapper (20). A read-only call that ran in a parallel batch skips the before-chain. New policies register a hook instead of editing the loop.
- **Session pruning** (`harness/pruning.py`). Before the context budget would pay a model call to summarise, tool results older than the newest three tool rounds and longer than 2,000 characters are cut to head and tail with a note on how to get them back. It starts at half the compaction threshold, changes messages in place, never prunes a message twice and waits for 25 % growth between passes, so the cached prompt prefix moves rarely. Only `role == "tool"` messages are touched.
- **Tool calls in text.** All hosts speak native function calling, so text is parsed only for explicit call syntax (JSON tool-call objects, fenced python-style calls, `tool_code`, gpt-oss harmony, Qwen XML). Command-like lines in prose are never run: they are how a quoted web page would inject a command.
- **Repeats.** One guard (`harness/loop_guard.WorldClock` inside `run_agent`): an identical call with nothing changed since is answered from memory; a volatile read (`read_terminal`) may repeat three times. The runner no longer adds a second throttle.
- **Queue.** One turn runs at a time. Messages typed meanwhile wait in `ChatService._follow_ups`; when the turn ends, the next one is folded together with the messages queued right behind it for the same thread (OpenClaw's *collect* mode), so three quick messages are one turn. Hand-offs, problem reports, `/templates` and `@mentions` are never merged. Steer still injects into the running turn.

## 4. Cat Crew: intent router and SOP pipeline

**Cat Crew** is the orchestrator and system chat. It is *not* an agent: it has no rows in `agent_tools` / `agent_skills`, no column in the Skills / Tools matrices, and its skill index is the global skills only (skills and tools are assigned to the specialist cats; Cat Crew uses built-in engine routing). Its wire id is `crew`; the legacy id `chief` (old sessions, ledger rows, links) is folded into it on read, and the `chief` SQLite table (its config: name, prompt) keeps its name. Every message to it goes through `platform/orchestrator.classify_intent` — a deterministic, unit-tested router with no LLM call and no permission check:

- `chat`: questions, remarks, planning → a free-form turn with the primary model (`ChatService` starts a `TurnRunner`, prompt from `platform/chief.build_chief_prompt`, read-only lookup tools plus `hand_off_to_crew`). The model can ask for delegation with `hand_off_to_crew(brief, roles?)`; the tool only records the request (`platform/handoff.py`) and the service starts a normal `work` turn when the chat turn ends, so the cats stream over the WebSocket instead of running invisibly inside a tool call.
- `work`: a build/fix/design/test/deploy/write request → the SOP below. A whole app (or nothing specific) runs the full pipeline; otherwise only the roles the request calls for run (`roles=` on `run_project_room_turn`, pipeline order, plain "do what was asked" task text).
- `mention`: `@name` → that cat directly.

`platform/sop.py` runs the phases in a fixed order. Each phase resolves a bot by role from the project's staff, opens a ledger task, runs the specialist, records its output and moves on.

| Phase | Role | Cat |
| --- | --- | --- |
| blueprint | `prompt_engineer` | Cipher |
| architecture | `vanguard` | Vanguard |
| distribution | `vanguard` | Vanguard |
| devops | `devops` | Forge |
| build | `developer` | Pulse |
| design | `designer` | Pixel |
| qa | `qa` | Aegis |

Legal (Lex) and the accountant role join when the brief matches keywords. If QA fails, the pipeline sends the failure to a developer for a fix and re-runs QA once. An `@name` mention skips the pipeline and runs that cat directly. A steering message typed mid-run is folded into the next specialist's context as the highest-priority note.

### One engine, cats as profiles (and the optional shared history)

There is one engine (`core/CatCrewEngine`); a cat is a profile applied to it: `platform/cat_profiles.py` renders each registry cat as a `CatProfile` (`id`, `name`, `role`, `system_prompt`, `allowed_tools`, `avatar_icon`; `GET /api/cat-profiles`). It is a view over the registry, not a second config file, so the prompt edited on the Agents page is the prompt that runs. `allowed_tools` is exactly what the turn is bound to: the role's built-in pack (essentials first) plus the registry tools assigned to the cat; the runner refuses anything else (`_tool_allow`).

Each hand-over emits `cat.swapped` (`{cat_id, name, phase, label, status}`) next to `phase.started`; the UI keeps it as `room.activeCat` and the Cat Crew header shows "Pulse · Phase 4: Build". Fleet cards, avatars and per-cat chat bubbles are driven by `bot.activity` / `chat.message` as before.

Context modes (`CATCREW_UNIFIED_CONTEXT`, default `0`):

- **Isolated (default).** Every run starts from its cat's system prompt plus its assignment and a capped hand-off. Nothing is duplicated (a run's transcript is not shared), the system prompt is stable per cat, and no cat reads another cat's tool noise. This is the project's context-isolation rule.
- **Unified (`1`).** A work run (SOP turn or problem report) owns one `SharedThread` (`platform/shared_context.py`): one list of messages all its cats read; a hand-over swaps only the system message (the mask) and the tool binding. A finished cat's transcript is collapsed to its assignment line, its result and the files it touched (bounded to about 14k characters), and the active cat's assignment is marked `[assignment for Name (role)]` so compaction keeps pinning it. Costs to measure before making it the default: the changed system message defeats provider prompt/KV cache reuse across cats, and each cat now reads the others' results in addition to the hand-off. Compare with `scripts/smoke_project_run.py` (the `[ctx]` lines show `shared history of N message(s)`).

### Problem reports: bug -> lead -> fix plan -> fix -> QA

A user who sees something wrong reports it (the "Report problem" button in a cat's chat or in Cat Crew, `POST /api/projects/{pid}/threads/{bot_id}/report`). Both chats start the same flow (`platform/bugflow.run_bug_turn`, run as one turn in the Cat Crew room so every cat's activity is visible there; each specialist's turn is also mirrored into its own thread):

1. A `bug` task in the ledger (`kind='bug'`, `reported_by` = the cat whose chat it came from, or `user`), assigned to Vanguard.
2. Vanguard runs in a fresh context with the report and ledger facts (the reporter's last tasks and files, recent file changes). It writes the plan by calling the essential tool `create_fix_task` once per step (at most 6; assignee must be a fixing cat on the project; `acceptance` required; `depends_on` optional). Each call is a `fix` work order (`parent_id` = the bug), so the plan is data the harness runs, not prose it parses. If the lead writes prose only, one fix is created for the reporter (or the developer) with the lead's notes.
3. Each fix runs as its own work order: its instructions, its acceptance criteria and a 1.2k-character plan excerpt. No conversation history.
4. QA verifies the acceptance criteria (`kind='review'`). A FAIL (including a stuck QA turn) becomes a "Fix again (n)" step for the same cat with QA's verdict, at most `MAX_FIX_ATTEMPTS` (2) times, then QA runs again.
5. The bug closes `done` only on a QA PASS; otherwise `failed` (QA still rejects), `unverified` (no QA cat) or `blocked` (stopped). Vanguard's closing message lists the steps and the outcome.

Ledger work-order columns (additive migration, old rows read as `build`): `kind` (build | bug | plan | fix | review), `parent_id`, `acceptance`, `depends_on` (comma-separated task ids), `attempt`, `reported_by`.

## 5. Thread-safe SQLite and the async pipeline

Two SQLite files with different jobs, both accessed with **short-lived connections** (never a connection shared across threads):

| File | Module | Contents | Concurrency control |
| --- | --- | --- | --- |
| `data/platform/catcrew.db` | `db/ledger.py` | Operations ledger: `projects`, `project_members`, `project_member_tasks`, `project_member_task_results`, `file_changes`, `skills`, `agent_skills`, `tools`, `agent_tools` | A process-wide `threading.Lock` serialises every write; every function opens and closes its own connection (`timeout=10`, `busy_timeout=5000`); WAL journal mode with `synchronous=NORMAL`, so API reads never block a turn's writes; schema created lazily on first connection with `CREATE TABLE IF NOT EXISTS` plus additive `ALTER TABLE ADD COLUMN` steps |
| `data/platform/catcrew_state.db` | `db/state/db.py` + `core/supervisor.py` | `runs` (one row per delegated run, with parent links) and tables reserved for a later registry migration | Context manager that commits or rolls back and always closes; WAL journal mode; the supervisor writes state transitions (`spawn`, running, done or failed) |

Migrations are additive only. No code path drops or rewrites an existing table.

Delegation is asynchronous even though the caller sees a plain function. `run_delegated` starts a `CatCrewEngine` (a dedicated thread running an asyncio loop), spawns an `AgentRun`, waits for it, and stops the engine. `RunSupervisor.spawn/wait/cancel` track the run and its descendants; `LocalInferenceSemaphore` remains for runs bound to a single local resource; every model host is a cloud host now, so model runs do not queue on it. Developer runs are followed by `verify_and_heal`, which runs the build check up to three times and spawns a healing child run on failure.

The identity catalog (`registry.json`) is still a JSON file with a process-global cache, now guarded by one `RLock`, written atomically (write, `fsync`, `os.replace`) with the previous version kept as `registry.json.bak`. A catalog that cannot be parsed is moved aside as `registry.json.corrupt-<time>` (never overwritten) and the `.bak` is loaded instead. At start-up, `runs` rows a previous process left `queued` / `running` / `paused` are marked `failed` (`RunRepo.reap_orphans`, error `app exited`). Still open: the `runs` writes happen synchronously on the event loop. See the "Async and DB bottlenecks" section of the backlog.

## 6. Dual Skill / Tool engine

CatCrewAI separates knowledge from capability.

**Skills are playbooks.** A skill is a Markdown file with frontmatter (`name`, `description`, `version`, `target_roles`) in `backend/skills/<name>/SKILL.md`, an optional `CATCREW_HOME/skills` folder, or a project's `.cat-crew-ai/skills`. Only a compact index (name and description) goes into the prompt; the body is loaded lazily when the agent calls `read_skill`. The `skills` table records catalog metadata and `agent_skills` is the per-agent assignment matrix (`is_global` skills are visible to everyone). `sync_skills_from_disk()` upserts what is on disk into the catalog by slug. After a task, `platform/auto_skill.py` may propose a new `auto_generated` skill; it is written unassigned and surfaced as a `skill_proposal` event for human approval.

**Tools are executables.** Letta-style plain Python functions live in `backend/tool_functions/` (or come from the marketplace, imported into `CATCREW_HOME/catcrew_marketplace_tools`). `platform/tool_registry.function_to_schema` turns a function's signature and docstring into a JSON schema for native function calling. The `tools` table stores the slug, docstring, schema and a `module:function` handler path; `agent_tools` binds tools to agents. At the start of a turn `register_agent_tools(bot.id)` resolves handlers with `resolve_handler` and registers the schemas and executors through `harness.deferred.register_tools`, which keeps them in `ContextVar`s for that turn only. Connector (MCP) tools use the same deferred mechanism, so they cost no prompt tokens until an agent is allowed to load them.

**Essential and optional tools.** `platform/essentials.py` is the single source of truth for what a cat can never be without. Essential built-ins per role (`ESSENTIAL_BUILTINS`: every specialist gets `read_skill`, `update_todo`, `report_task_results` and the read tools; writers get `write_file` / `replace_in_file` / `create_directory`; builders get `run_command` and git reads; QA gets `browser_check` and the smoke test) are prepended by `builtin_names_for_role`, so an agent's own `tools` list can only choose among the optional ones. Essential registry tools (`ESSENTIAL_ROLE_TOOLS`, e.g. Aegis's browser set, Pulse's `write_file_patch`) are re-attached by `ensure_role_tools` on every start, bound by `register_agent_tools` even if the assignment row is missing, shown with a lock in the Tools matrix, refused by `PUT /api/tools/{id}/assignments` (the cat keeps them) and by `DELETE /api/tools/{id}` (409). Everything else (web search, image generation, `browser_look`, `browser_select_option`, `read_code_ast`, Docker and VPS probes...) is optional and toggled in the Tools page. `GET /api/tools` reports `locked_agent_ids` per tool.

Built-in tools (files, shell, git, database, web, images) live in `backend/tools.py` and are selected per role by `builtin_names_for_role`. The role tools (Pulse, Forge, Aegis, plus the browser set for Aegis and Pixel) come from the registry: `platform/role_tools.py` registers and assigns them at start-up (`ensure_role_tools`, idempotent). A version marker in the SQLite `meta` table (`role_tools_version`) means an existing install receives only assignments that shipped after its marker, so a tool the user unassigned on the Tools page is never re-added; `scripts/seed_role_tools.py` forces everything.

## 7. `report_task_results` and activity

Every specialist ends its work by calling the `report_task_results(task_id, summary, status)` tool. This replaces inferring completion from chat text.

What actually happens, in order, inside the tool call on the specialist's own thread:

1. Look up the task in `project_member_tasks`; unknown ids are rejected with an error message the model can read.
2. `db.add_task_result` inserts the result row (summary capped at 8000 characters) and sets the task's status in one transaction.
3. `refresh_project_structure_doc` rewrites `PROJECT_STRUCTURE.md` in the project's shared folder from the ledger: tasks grouped by status and the fifteen most recent file changes. This is the "notification to Vanguard": a cheap, best-effort document rebuild rather than a second agent turn, so there is no recursive agent call from inside a tool.
4. On a successful status, `auto_skill.maybe_propose_skill` may make one small, no-tools model call to judge whether the task produced a reusable pattern.

Important: this tool is synchronous. Steps 2 to 4 finish before the tool returns, and step 4 is a blocking model call. The design brief describes it as asynchronous; making it so is item A-05 in the backlog.

**Timeline and live status.** All agent activity is a typed event stream. `harness/events.py` defines the events (`turn_start`, `activity`, `tool_call`, `tool_result`, `approval_required`, `auth_required`, `ask_user`, `skill_proposal`, `turn_end`, `error`); `emit()` appends each one as a JSON line through `trace.log_event` to `data/traces/<session-id>.jsonl`, keyed by a session id held in a `ContextVar`. `ActivityRecorder` (`core/activity_recorder.py`) folds that stream into the numbered steps a chat turn shows, and the chat stores them on the assistant message (`activity: {elapsed_s, steps}`), which the UI renders as a two-line execution card with a "See more" toggle. For live status, `platform/activity_board` keeps a thread-safe in-memory map of what each bot is doing and publishes every change to the event bus (section 2), so nothing polls.

## 8. Frontend architecture

- **State.** `state/reducer.ts` is a pure `reduce(state, event, now)`: every WebSocket event maps to a state patch, and nothing else mutates live state. `state/store.ts` (zustand) holds the actions (bootstrap, load a project, send a message, resync); `state/ws.ts` is a reconnecting socket (back-off, ping, stale-socket detection, `hello` -> resync); `state/live.ts` wires them together once. Components read slices of the store and never open a socket.
- **Pages.** Home is a **launcher only** (recent projects, New project, Open folder); it shows no tasks. The project workspace has three columns: a **left sidebar with only the Fleet** (the cats working in the project; no "Add a cat" button, because cats join and leave through `bot.staffed` / `bot.released`), the **Cat Crew** chat, and a collapsible **right Inspector** (`RightInspector.tsx`) with the tabs Telemetry, Tasks and Changes. Each task also appears in the chat as an execution card. The Inspector is opened and closed from the room header (gauge icon, next to Terminal and Settings; its state is in `localStorage` `catcrew.inspectorOpen`, open by default on windows 1280 px wide or more, and the button shows a red dot when the context is above 85 %). While it is closed nothing in it is mounted, so nothing polls. Both side panels are resizable with `state/useResizableWidth.ts` (`edge: "left" | "right"` says which way a drag grows the panel; the chat keeps at least 480 px). Skills and Tools are assignment matrices (skill or tool x cat, plus a global column); Agents and Models manage the crew and the per-role model choice. **MCP Tools & Integrations** (`pages/Integrations.tsx`, `/#/integrations`) is its own page — `McpPanel` (server status/tools) and the "service"-group `ServiceKeysPanel` (Brave Search and any other non-chat-host key) — kept separate from Models, which now only covers chat hosts and per-role model choice.
- **Cards.** `ExecutionCard` and `DiffBlock` are clamped to two lines (`line-clamp-2`) and expand with "See more" into the full numbered log, previews and diffs. Long message text is collapsed the same way by `CollapsibleText` (used by `MessageView`): a cat's work report (a pipeline phase) shows 5 lines, a conversation reply or a user message 12, each with a soft fade and "See more (N more lines)" / "Show less", and nothing collapses when only one or two lines would be hidden. The clip is CSS only, so the full text stays in the DOM. A live card shows the running turn's steps; when the cat's message arrives the steps freeze into that message.
- **Time.** `lib/time.ts` renders "just now", "X mins ago" and "X hours ago" under 24 h and an exact date afterwards; a shared clock hook re-renders labels every 30 seconds.
- **Window lifecycle.** The Tauri window is declared `visible: false` with the app background colour in `tauri.conf.json`, so the OS never paints an empty frame. After React's first painted frame (`lib/window.ts`, two `requestAnimationFrame`s) the UI calls `show()`. The Rust shell shows the window itself after 4 s as a failsafe, starts `python -m backend` when nothing answers on the loopback port (or attaches to a backend that is already running), and stops it on exit with `POST /api/shutdown`, then `kill` as a last resort. The window uses native decorations with the dark theme; a custom titlebar is not used.
- **Start-up handshake.** The shell starts the engine and opens the window at the same time, and the engine needs a few seconds to listen, so an unreachable backend is the *normal* state at launch and is never shown as an error. `App` renders `BootGate`: until the first `/api/bootstrap` has loaded (`ready`), the window shows `StartupScreen` (logo, spinner, "Starting the engine…", and after 6 s a calm "still starting" note). `state/boot.ts` `runBoot` (driven by the store's `connect()`) keeps asking quietly with a short back-off and gives up only when the engine has clearly failed: the shell says so (`backend_status`), the backend answered with a real error (a non-network `ApiError`, which is not retried), or 30 s passed in silence. Then the same screen shows the reason, the tail of the engine's output under "Details", and **Try again**. If the engine shows up later, the socket's `hello` resync loads the data and the gate opens by itself. The shell side (`src-tauri/src/lib.rs`): `BackendStatus` is `starting`, `ready`, `external` or `failed {detail}`; a failed spawn (no Python) is reported at once, and a process that dies while starting is noticed in about 200 ms (`wait_until_ready`) with the last 14 lines of its stdout and stderr as the detail. Read it with the Tauri command `backend_status`.
- **System tray and close-to-tray.** `app.trayIcon` in `tauri.conf.json` declares the tray icon (`icons/32x32.png`, id `main`); `setup_tray` in `src-tauri/src/lib.rs` attaches the menu ("Show CatCrewAI", a separator, "Quit CatCrewAI") and the click behaviour: a left click toggles the window (hidden or minimized: unminimize, show, focus; on screen: hide), a right click opens the menu. The window's "X" (`WindowEvent::CloseRequested`) is intercepted: the close is prevented, the window is hidden (the taskbar entry goes with it, `skipTaskbar` stays `false` for the visible window) and a system notification, "CatCrewAI is running in the background.", is shown once per run (`tauri-plugin-notification`). The only ways to really quit are the tray's Quit item and the sidebar's Power Off button, which calls the Tauri command `quit_app`: both go through one idempotent `quit()` that hides the window, stops the backend this shell started (`POST /api/shutdown`, then `kill`) on a worker thread (never on the UI thread) and calls `app.exit(0)`. A backend the shell merely attached to (already running, or `CATCREW_BACKEND=external`) is left running. Once a quit has begun, close requests are no longer turned into hides.

## 9. Models: discovery, health and token routing

**Roles.** `services/settings_store.py` stores one `{host, model}` per role: Chat (`companion`), Coding, Memory, Vision, Planning and Images (ComfyUI). Chat is required; the other text roles inherit Chat when unset (`core/provider_factory.provider_if_explicit(role)` returns a provider only when the user picked a model, so Vision and Planning never switch models by accident). Hosts are cloud hosts only: OpenRouter (every vendor's models through one key, by vendor-prefixed slug) and the vendors' own OpenAI-compatible APIs (OpenAI, Anthropic, Google Gemini, DeepSeek, Groq, Mistral, xAI), all through one client (`providers/openai_compat.OpenAICompatProvider`; `OpenRouterProvider` adds routing and prompt caching). `services/api_access.CATALOG` is the one table of every key CatCrewAI keeps -- the model hosts, Brave search and TypeSafe (Jev) -- write-only through `/api/keys`. There is no local model host: LM Studio was removed, and a `lmstudio` / `ollama` pick saved by an older version reads as unset (`settings_store._migrate_chat_host`). Images run on ComfyUI, an OpenRouter image model, or Off.

**OpenRouter prompt caching.** `providers/openai_compat.OpenAICompatProvider` (which `OpenRouterProvider` subclasses) can inject an Anthropic-style `cache_control: {"type": "ephemeral"}` breakpoint into the system message before sending it (`_cache_messages`, non-mutating — it returns a new list rather than editing the shared `messages` array a run keeps across rounds and can hand to a different provider via `swap_provider`). OpenRouter passes this straight through to providers that support prompt caching and ignores it as a no-op on providers that do not; OpenAI/Grok/Moonshot/Groq/DeepSeek/Gemini 2.5 cache automatically with no breakpoint needed, Anthropic/Qwen need the explicit one this app sends. It defaults on (`config.OPENROUTER_PROMPT_CACHING`, default `1`) and cuts input-token cost on repeated calls with the same system prompt and tool declarations. `usage_meter.py` reads back whatever cached-token count the host reports (`usage.prompt_tokens_details.cached_tokens`, falling back to the Anthropic-native `cache_read_input_tokens` / `cached_tokens` fields OpenRouter passes through) and exposes it as `UsageMeter.cache_savings()` for the Telemetry tab. `estimated_pct_spend_saved` there stays a documented assumption (`CACHED_TOKEN_DISCOUNT = 0.9`); `estimated_usd_saved` (`_estimate_cache_usd`) turns that into a real dollar figure by pricing the cached tokens against the calling model's own price from the OpenRouter catalog snapshot (`model_discovery.peek_snapshot`) — `null` when that model's price is not in the current snapshot.

**OpenRouter savings & routing extras** (`services/settings_store.openrouter_settings`, `GET/PUT /api/openrouter/settings`, `docs/API.md`). Beyond caching, three optional knobs feed `services/api_access._openrouter_routing_body()`, which every OpenRouter request carries via `OpenAICompatProvider`'s `extra_body`: `provider_sort` (`""` OpenRouter's own price-weighted default / `"price"` / `"throughput"` / `"latency"`) becomes the request's `provider: {sort, allow_fallbacks}` object — this is the real mechanism behind "route to the fastest/cheapest provider automatically"; **OpenRouter has no `:auto` model-slug suffix**, so despite that being the literal ask, none is appended anywhere (`:nitro` / `:floor` *are* real per-model suffixes and need no code here — the user can just type one into a model field). `compression_enabled` turns on OpenRouter's `context-compression` plugin (`plugins: [{"id": "context-compression"}]`, the real mechanism behind what OpenRouter used to call "middle-out" transforms) for requests over an endpoint's context window; it can drop/truncate messages OpenRouter-side, so it defaults off rather than being force-enabled on the heavy system prompts. `free_tier_enabled` / `free_tier_model` (`services/aux_routing.route(host, model)`) reroute CatCrewAI's own lightweight background calls to a `:free` model instead of the configured one; the one call site wired up today is context-summary compaction's Memory-role call (`services/compaction.py::summarizer_provider`) — the Coding/Planning/Chat roles are never touched by this toggle, since misrouting the model actually doing the work to a free tier would be a correctness regression, not a saving. The Model Picker's pricing (see Discovery below) reuses the same catalog snapshot these features price against, rather than a second fetch service.

### Jev ("System One") pre-execution gatekeeper

`backend/middleware/jev_gatekeeper.py` is a decision interceptor in front of `BaseProvider.run_agent`, off by default (`enabled: false`) and reached through **OpenRouter's Decisions endpoint** — `https://openrouter.ai/api/alpha/decisions`, model slug `typesafe/jev-latest` — riding on the **OpenRouter key already configured for chat models** in the normal case (`_resolved_key()`: explicit saved override → `CATCREW_JEV_KEY` env override → `services/api_access.resolved_key("openrouter")`); Settings → Models → Jev gatekeeper only offers the optional override, not a required key of its own. It has two jobs, named after Kahneman's System 1 / System 2 split since no deterministic-action dispatcher exists in this codebase to build a literal "skip the LLM" path on:

1. **Precheck (once per turn, before the coding model runs).** `precheck_intent()` asks Jev, in one round-trip, a single `noul` (yes/no-probability) question: can this be answered directly with no tools? Jev never drafts a reply — System One models are pure classifiers, there is no `answer_text` anywhere in this wire format — so when confidence is above `BYPASS_CONFIDENCE` (0.95, fixed, not the configurable slider) the caller still calls the coding model for the actual reply, just **without the tool schemas attached**; that missing ~30-tool-definition JSON blob is where the saving comes from, not skipping the call. A low-confidence or failed answer falls through to the normal tool-enabled loop, so the worst case is one avoidable round of tool schemas, never a wrong or missing answer.
2. **Guard (on every sensitive/destructive tool call the model generates).** `guard_tool_call()` runs after `harness.approvals.gate_tool()` and before execution: for a call in the guarded set (`harness.approvals.DEFAULT_DESTRUCTIVE` plus any `mcp__…` / `connector__…` / `mcp_call_tool` call, minus a small `_ALWAYS_ALLOW` allowlist of read-only tools so trivial calls skip the extra latency and cost), Jev answers a `noul` "is this safe and on-goal?" question; a confidence below the configurable `confidence_threshold` (default `0.92`, `settings_store.jev_settings()`) blocks the call before it runs, the same `None` = allow / `str` = deny shape `gate_tool()` already uses.

`services/jev_client.JevClient.decide(state, questions)` is the wire adapter, posting to OpenRouter's Decisions endpoint by default: `POST https://openrouter.ai/api/alpha/decisions`, `Authorization: Bearer <the resolved key>`, a JSON body of `model` (`typesafe/jev-latest` by default) + `state` + a `questions` map keyed by question id, each a `noul` / `choice` / `score` primitive (`services/jev_client.PRIMITIVES`); the response is an `answers` map, one entry per question id. This wire format is identical to TypeSafe's own direct API (`https://api.typesafe.ai/v1/systemone`) — only the host, key and model-slug prefix (`typesafe/jev-latest` vs `jev-latest`) differ — so a `base_url`/`CATCREW_JEV_URL` override still works as an escape hatch to TypeSafe's direct endpoint. **Caveat**: the `/api/alpha/decisions` path reflects OpenRouter's own "beta" framing plus two independent third-party reports and has not been confirmed against a live authenticated call from this codebase (see the module docstring in `services/jev_client.py` for what to check if Jev never records a successful decision). Documented jaggedness this client's callers work around: Jev reads `state` at face value (no arithmetic, no date reasoning, no multi-hop inference) and does not treat it as adversarial, so both call sites keep `state` short and scoped rather than expecting Jev to notice something is "off"; and TypeSafe's docs note `P(x) != 1 - P(not x)` across two separately-worded questions, so both call sites ask one `noul` question in the exact polarity they need and read the probability directly, never derive it by negating a complementary question. Any failure (network, an unrecognised model, a malformed response) never raises: `decide()` returns one `Decision(ok=False, ...)` per question instead, and every caller treats `ok=False` (or low confidence) as "no opinion, let it through" — Jev exists to save tokens and screen for safety, never to become a new reason a turn cannot proceed. `services/jev_metrics.py` keeps thread-safe in-memory counters (precheck/guard calls, bypasses, blocked calls, a rough tokens-saved estimate, average decision latency over the last 500 decisions), read by `services/telemetry._jev()` for `GET /api/telemetry/live` (which also turns the tokens-saved estimate into a dollar figure the same way `openrouter_cache` does, and always strips the raw key before returning) and directly by `GET /api/jev/metrics`. Settings (`GET/PUT /api/jev/settings`) live in the `jev` section of `settings.json` alongside the rest of `brains`/`api_access`; the optional override key is managed only through this route, deliberately kept out of the generic `/api/keys` catalog (`api/routes/keys.py`) since Jev is neither a chat host nor one of that catalog's "services" and would be miscategorised in the UI either way — and because in the normal case there is no key here to manage at all.

**Frontend** (`components/models/`). `JevGatekeeperPanel.tsx` and `OpenRouterSavingsPanel.tsx` sit side by side on the Models page. The Jev panel's main state is a `KeyBadge` showing where its key comes from — `"openrouter"` (riding on the OpenRouter key, the normal case), `"saved"`/`"environment"` (an explicit override is in effect) or `"none"` (no OpenRouter key configured yet, shown with an inline warning) — plus a "Use a different key" button that opens a small advanced-only `JevKeyOverrideModal` (modelled on the generic `KeyModal.tsx`, but posting to `/api/jev/settings` instead of `/api/keys/{id}`); this follows the same established key-entry convention enforced by an existing test (no `input[type="password"]` sits in the DOM at rest). `KeyBadge`'s `source` prop is typed as `JevKeySource` (`KeySource | "openrouter"`, `lib/types.ts`) so it can show the OpenRouter case without widening the shared `KeySource` type every other key consumer (`HostsPanel`, `ServiceKeysPanel`) uses. `CapabilityBadge.tsx` exports `ModelBadges` (all capability badges grouped together) and `PriceText` (pricing rendered separately, after the badges, not interleaved with them); `ModelPicker.tsx` renders both next to every model, and also adds a search field, Vision/Tools/Free filter checkboxes, and a cheapest-first sort (input price primary, output price tiebreak) to the dropdown. `lib/telemetry.ts`'s `fmtUsd` appends `(~$X.XX)` to the cache/Jev telemetry lines once `estimated_usd_saved` is non-null.

**Per-project overrides** (`services/model_resolver.py`). `settings.json` keeps `project_model_roles[project_id][role] = {host, model}` next to the global `brains`. `get_effective_model(project_id, role)` is the one place that answers "which host and model, and with which key": project override, else the global pick, else (unset roles) Chat. `core/provider_factory` (`provider_for_turn`, `provider_for_role`, `provider_if_explicit`, `caps_for_current`) takes the project id and asks it; the id reaches deep callers (compaction, vision, image checkpoint) through the `current_project_id()` context variable that `run_bot`, `TurnRunner` and `RoomRunner` set for the length of a turn. The API is `GET/PUT /api/projects/{id}/models` (`docs/API.md`), the UI is Project Settings -> Project Model Overrides (`#/project/:pid/settings`), and the Models page says its picks are the global defaults. An override on a host that has lost its key is ignored, so a project never fails on a missing key it did not use before.

**Discovery** (`services/model_discovery.py`). Every host is asked with `fetch_openai_compat` -- its OpenAI-shaped `/models` list (retired `active: false` entries dropped, Gemini's `models/` prefix stripped, Anthropic's headers added). For OpenRouter, `_pricing(name, info)` also reads that same response's `pricing` object straight off each model — `price_prompt_per_1m` / `price_completion_per_1m` (scaled from OpenRouter's USD-per-token strings), `is_free` (a `:free`-suffixed slug or zero pricing both ways) and `supports_prompt_cache` (`pricing.input_cache_read` present) — onto `LmModel`, so the pricing dropdown asked for in the UI is the existing discovery/caching pipeline with four more fields, not a second catalog service or fetch. Keys go in headers. A failure never carries a URL, a key or a raw exception; it is classified as `no_key`, `auth`, `unreachable` or `error`. Results sit in a 30 s cache (`cached_snapshot`; a key change or a refresh clears it), and the probe runs off the event loop. `peek_snapshot(host)` reads that cache without triggering a probe — used by `usage_meter`/`telemetry` to price cache/Jev savings without adding a network round-trip to a telemetry read.

**Capabilities** (`services/model_caps.py`). `classify(name, meta)` returns `vision`, `reasoning`, `tools` and `chat`. What the host reports wins; the model name is the fallback and is matched on whole words (`r1` does not fire inside another token). Embedding and image-generation models are kept out of the pickers. `ROLE_NEEDS` states what each role works best with; the UI only warns.

**Health** (`services/model_health.py`). For every role with a model picked, the host is probed (in parallel, one probe per host) and the model is looked up in its list. The result is a plain report, `{ok, hosts, issues[]}`, with a ready-to-show sentence per problem (`missing`, `offline`, `no_key`, `disabled`). It is computed once in a background thread at start-up, cached for 60 s, computed by one caller at a time, and dropped when a role or key changes. `GET /api/models/health` serves it; on launch the UI's `useModelHealth` store asks once and `ModelNotice` opens the **Model Configuration Notice** when there are issues, and the Models nav icon carries a badge while any remain.

**Token routing** (`services/compaction.py`, `providers/base.py`). `BaseProvider.run_agent` runs a `ContextBudget` before every model call. When the whole conversation (system prompt included) reaches the threshold of the model about to be called it summarises the older turns with the Memory-role provider (Chat when unset), keeps the most recent turns verbatim (the newest messages that fit in `CATCREW_COMPACT_KEEP_TOKENS`, default 20,000 estimated tokens, at most half the threshold, never fewer than 4 messages; `0` falls back to `CATCREW_COMPACT_KEEP` messages), never separates a tool call from its result, and retries only after the history has grown 25 % again. The threshold is not a constant: `services/provider_limits.get_model_context_limit(host, model)` gives each model's window and the summarise-at size (about 85 %). For `openrouter`, the vendor prefix of the model slug picks the window (`vendor/model` -> vendor): `deepseek/...` 64k / 54k, `google/...` 1M / 850k, `anthropic/...` 200k / 170k, `openai/...` 128k / 110k, any other vendor 64k / 54k (the default fallback). The vendors' own hosts use their table row; an unknown host gets 16,384 / 14,000. `run_agent` passes the current provider on every round, so a run that swaps model mid-way is measured against the new window; the gauge (`context.usage`, `/api/telemetry/live`) uses the same window. `CATCREW_CONTEXT_TOKENS` (default `0` = automatic) forces one threshold. The summary replaces the old turns for the request that follows; the turn's activity card gets a "Compressed context" step. Planning: `platform/sop._planning_provider` runs the architecture and distribution phases on the Planning model when one is set. Vision: `browser_look` (below) is the only consumer.

**Browser tools** (`tool_functions/qa_tools.py`). Aegis and Pixel drive one Playwright page each (keyed by the cat's id). Playwright's sync API is bound to its thread, so every call goes through a single dedicated worker thread. The tools are text-first: `browser_snapshot` (what is on the page, with CSS selectors), `browser_inspect` (computed style, contrast ratio, overflow) and `browser_set_viewport` give a model without vision the facts a screenshot would, so choosing a chat model without vision cannot break them. `browser_take_screenshot` only writes a PNG for the user. `browser_look` sends a screenshot to the Vision-role model as an OpenAI-style `image_url` part and returns its description as text; with no Vision model set it answers that and points to the text tools. Only `http(s)` URLs can be opened.

### The integrated terminal

`services/terminal_service.py` (not the agents' `services/terminal.py`, whose process-tree kill it reuses) and `api/terminal_ws.py`. A `TerminalSession` is one project's terminal: a tracked working directory, at most one running command, stdout and stderr read on separate threads and pushed to the socket through `loop.call_soon_threadsafe`, stdin forwarded to the running process, interrupt = kill the tree. There is no PTY and no native dependency, so it is line oriented; the frontend renders the colour codes (`lib/ansi.ts`, a small SGR parser with `\r` line rewriting for progress bars). `TerminalService` keeps one session per project (cap 8), replaces the old one on reconnect and remembers where it ended. Cleanup: the shell dies with its WebSocket (page left, project switched, panel component unmounted), with the project when it is deleted, and `_shutdown_runtimes` calls `close_all()` when the app exits. Collapsing the panel only hides it, so a dev server keeps running until you leave the project. Upgrade path if full-screen programs are needed: a PTY (`pywinpty` / `pty`) in `TerminalSession._spawn` and xterm.js in `TerminalPanel`, the socket protocol stays.

### Live model telemetry

The **Telemetry** tab (`components/ModelTelemetry.tsx`, formatting in `lib/telemetry.ts`) answers "how is the model doing" without asking a cat. Backend pieces:

- `services/usage_meter.py`: a thread-safe in-process meter. `OpenAICompatProvider` records every call (`record_call`: host, model, provider-reported `usage` or, when the host sends none, the characters / 4 estimate; streaming asks for `stream_options.include_usage` and retries without it on a 400) and every failure (`record_error`, so a 429 is known). It keeps a sliding window of requests and tokens per host, the last model, the generation speed of local calls, per-call cached-prompt-token counts (`cached_prompt`, OpenRouter only, see prompt caching above) and, per project, the last context reading. `cache_savings(host="openrouter")` sums those into the Telemetry tab's prompt-cache card, including `estimated_usd_saved` (`_estimate_cache_usd`: cached tokens priced against that call's model in the OpenRouter catalog snapshot, `null` when the model isn't priced there). `BaseProvider.run_agent` calls `report_context` right after `ContextBudget.apply`: that stores the reading and publishes `context.usage` on the bus (so it reaches the browser over `/ws/events`). Deleting a project forgets its reading.
- `services/balances.py`: OpenRouter `GET /api/v1/credits` (total credits minus usage; the one cloud host, so the one balance), key from `api_access`, a 60 s cache, marked stale after a call, failures reduced to fixed sentences.
- `services/jev_metrics.py`: the Jev gatekeeper's counters (see above), read for the `jev` section of the snapshot.
- `services/hardware.gpu_stats()`: NVML when `nvidia-ml-py` is installed, else `nvidia-smi`; the GPU with the most VRAM; 1.5 s cache.
- `services/telemetry.live(project_id)` puts them together (each part in its own try/except); `api/routes/telemetry.py` serves it as `GET /api/telemetry/live`.

Frontend: the tab polls the endpoint every 5 s while it is open and again when the project's turn changes, and takes the newer of the polled context and the live `rooms[pid].context` from the reducer, so the gauge moves with every model call. Green below 60 %, yellow from 60 to 85 %, red above (compression is about to run). Not measured: per-project balances (a key is global), and the generation speed of cloud hosts.

## 11. MCP integrations (Blender, Unity)

CatCrewAI does not ship a tool for every program a cat may drive. A program with an MCP server is plugged in through `backend/config/mcp_servers.json` and `services/mcp_service.py`, which uses the official `mcp` SDK (v2 API; `mcp>=2.0.0,<3` in `requirements.txt`).

**MCPManager** (`get_manager()`, a singleton started in the app lifespan, stopped on shutdown, off with `CATCREW_MCP=0`) owns one background asyncio loop. The engine is threaded and synchronous while the SDK is async, so each server is a long-lived supervisor task on that loop (it enters and leaves the SDK client in the same task, as anyio requires) and the synchronous entry points (`call`, `refresh`, `reconnect`, `register_for_agent`) cross over with `run_coroutine_threadsafe`.

- **Transports:** `stdio` (the manager starts the server as a child process), `streamable-http` and legacy `sse`. Config values may use `${NAME}` / `${NAME:-default}`, expanded in memory only.
- **Status per server:** `connected`, `connecting`, `reconnecting`, `disconnected`, `disabled`. A dead server is retried with a back-off (2 s doubling to 60 s); *Refresh / Reconnect MCP* skips the wait and also re-reads the config file, so a server can be added, removed or changed without restarting FastAPI. A `probe` (a cheap tool call or a resource read) tells "the server process is up" from "Blender / Unity answers": `ready` needs both. There is no MCP ping in the v2 client, so the keep-alive is a fresh `tools/list`.
- **Tools:** every `tools/list` entry becomes a function-calling schema (`openai_schema`, names `mcp__<server>__<tool>`, missing or odd schemas repaired). Results are returned as text (images are saved under `data/mcp/` and referenced by path); an `is_error` result and a protocol error both come back as `Error: ...` so the model can react.
- **Per-cat binding:** `bind_to` lists the cats that get a server's tools. `platform/tool_registry.register_agent_tools` adds them to the *running turn* (`harness.deferred`, a ContextVar cleared for every run), so Blender's tools exist while **Pixel** works and Unity's while **Pulse** works; nobody else has them in the schema, and a call by another cat is refused. The 1:1 chat and the delegated runs both add one line to the system prompt (`prompt_note`) saying what is bound and whether the server is up.
- **Context frugality:** at most `max_tools` (24) tools per server are in the schema, `priority` patterns first; the rest is reachable through `mcp_find_tools` (search by keyword) and `mcp_call_tool`.
- **Approvals:** with `tool_approval` on, an MCP tool needs approval unless the server marks it `read_only_hint`; `mcp_call_tool` is judged by the tool it targets.
- **Unity compile-fix loop:** `services/mcp_features.py` adds `unity_compile_check` for Pulse: refresh + recompile, read the console, return each C# error as `file:line CSxxxx message` with the source lines around it (from `Assets/Scripts/`), capped at 8 calls per turn. Pulse edits with `replace_in_file` and calls it again (the `unity-mcp` playbook: at most 5 rounds, stop and report `blocked` if the same error repeats).

**Unity relay (second door).** `unity_relay` in `mcp_servers.json` is a stdio server (`relay_win.exe --mcp` from the user's `~/.unity/relay/`), bound to Pulse next to the HTTP `unity` one; its tools are `mcp__unity_relay__*`. A leading `~` in `command` / `cwd` means the home folder (`expand_path`). It has no `probe`, `priority` or `compile_check` because its tool names are not fixed here: `mcp_find_tools` lists what it exposes. Not connected = the Editor is closed or the executable is missing (the **MCP Tools & Integrations** page shows the reason and the hint).

**The other side.** Blender: the `mcp-blender` server (separate, optional `pip install mcp-blender`, AGPL-3.0) talks over a socket to an add-on running inside Blender. The add-on has no auto-start, so `integrations/blender/install_addon.py` installs it into every Blender config folder it finds and writes `scripts/startup/catcrew_mcp_autostart.py`, which enables the add-on and starts its socket server after Blender opens (`--dry-run`, `--uninstall`, `--source`, `--blender-version`, `--install-server`). Unity: `integrations/unity/CatCrewUnityMCP.cs` (an `[InitializeOnLoad]` editor script for `Assets/Editor/`, installed by `install_unity_helper.py --project <path>`) points MCP for Unity at the HTTP transport and starts the local server on project load (through the package's `MCPServiceLocator.Server`, else `uvx --from mcpforunityserver mcp-for-unity`), and stops what it started when the Editor quits. Menu: CatCrewAI > Unity MCP.

| Setting | Meaning |
| --- | --- |
| `CATCREW_MCP` | `0` switches the whole subsystem off (default on; the tests set it to `0`) |
| `CATCREW_MCP_CONFIG` | Path of another `mcp_servers.json` |
| `CATCREW_BLENDER_MCP_COMMAND`, `CATCREW_BLENDER_HOST`, `CATCREW_BLENDER_PORT` | The `mcp-blender` command and where Blender's socket listens (default `mcp-blender`, `127.0.0.1`, `9876`) |
| `CATCREW_UNITY_MCP_URL` | Unity MCP endpoint (default `http://localhost:8080/mcp`) |
| `CATCREW_UNITY_RELAY_COMMAND` | The Unity relay executable (default `~/.unity/relay/relay_win.exe`, run with `--mcp`) |

Limits worth knowing: the real tool names differ from the ones a brief may use (Blender `scene_info`, `material_create`, `render_image`, `execute_script`; Unity `manage_gameobject`, `read_console`, `refresh_unity`, `manage_build`, `manage_editor`, `run_tests`); binding is per server, so every tool of a bound server belongs to its cat, and `priority` lists both spellings. The probe and the `compile_check` arguments follow the current upstream servers and are configurable. Unity's `testing` tool group is off by default (`manage_tools` turns it on). The C# helper is syntax-checked but has not been compiled inside Unity.
